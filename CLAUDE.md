# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Product goals, the owner's decisions and working preferences, and open items are in `docs/HANDOFF.md`. Read it at the start of a session.


InvestHepi: a Next.js 15 (App Router, React 19, TypeScript) market-news site deployed on Vercel Hobby. It pulls headlines and prices, has an LLM write a briefing per section (summary, trend, events, movers, scenarios), runs a separate prediction job that makes buy/hold/wait calls twice a weekday per market, and grades those calls at each market's close. Sections are `interests` (per user), `world`, `us`, `vn` (Vietnam). Everything is designed to run on free tiers (Groq/Gemini, Upstash Redis, GitHub Actions), and that constraint drives much of the architecture.

## Project at a glance (Nov 17 2026, v18)

- **Goal (changed Nov 19 2026, v19):** news first. A curious reader, with or without a finance background, catches up on the important and interesting news, understands it, sees its effect on markets and the world, and learns general knowledge along the way. Predictions are a side goal (the impact part). Free tiers only; Vietnamese readers matter most.
- **Three jobs:** briefings (explain, no calls; Gemini Flash-Lite first), predictions (graded buy / hold / wait calls, two runs per market per weekday in local time; gpt-oss-120b first), and the track record (grades each call at its market's close, within the hour, then re-checked against the official close; feeds the record back into the prediction prompt).
- **Non-negotiables:** every prediction uses the latest data or says "unavailable"; every number the AI writes must trace to the data it was given (inputs are stored for audits); one timetable; every time labeled with its zone; free-tier budgets counted for every change.
- **Workflow:** HANDOFF first, questions as one numbered list, plan, "go", build, stress test on real data, docs, ask before merging, then scheduled check-ins (never waits) for deploys, closes and ticks.
- The owner's decisions, session summaries and open items are in `docs/HANDOFF.md`; the rest of this file is how the code works.

When compacting, keep the list of modified files, the test commands and open decisions.

## Commands

```bash
npm run dev                    # http://localhost:3000, data in .data/ as JSON
npm run build                  # must pass with AND without the AUTH_* env vars
npm run typecheck              # tsc --noEmit (there is no linter)
npm test                       # all offline suites via scripts/run-tests.ts: runs every one, prints a summary, exits 1 if any failed
npx tsx scripts/vntest.ts      # run one suite (each script is standalone)
npm run refresh -- world       # run the pipeline once from the terminal
```

Tests are plain `tsx` scripts using `node:assert`, not a framework. They mock `globalThis.fetch` (no network), set env vars at the top, then dynamically `import()` modules and route handlers and call `GET/PUT/POST` directly with `Request` objects. A suite prints `<NAME> OK` on success. New suites must be added to the `SUITES` list in `scripts/run-tests.ts`; v19 regression tests go in `scripts/v19/<topic>.ts`, which `v19test` runs each in its own process (the one place; the runner fails if a `*test.ts` file is not listed, and `npx tsx scripts/run-tests.ts v18test` runs a subset). A suite that reads the clock calls `pinClock("<ISO time>")` from `scripts/clock.ts` before importing `src/` so it passes on any day and hour; never build fixtures from the real clock. CI (`.github/workflows/ci.yml`) runs typecheck, tests and both builds on every push and pull request.

Gotcha: the store is `.data/` locally and `/tmp/invest-helper` when `VERCEL` is set, or `STORE_DIR` when set (the test runners give every suite and v19 part a fresh `STORE_DIR`, so runs never share state, even across worktrees). Caches persist between runs (e.g. `market:*` for 10 min, `px:last`, `vnlist`), so tests that need a clean store set `VERCEL=1` and `rm -rf /tmp/invest-helper` first. Stale `.data/` can make a test fail for reasons unrelated to the code, and some suites (v4btest) delete `.data/`, so re-seed before manual browser checks.

Price-layer modules keep in-memory state (Yahoo cooldown, chart/live caches); tests reset it with `resetYahoo()` and `clearPriceCaches()`. Test fetch mocks must handle Yahoo's batch endpoint (`/v8/finance/spark?symbols=A,B`, flat JSON keyed by symbol) as well as `/v8/finance/chart/`.

Local browser checks: run the production build (`npm run build` then `npx next start -p <port>`); stop it with `pkill -f next-server` (the process isn't named "next start", so an old server can keep the port and serve stale HTML whose chunks 404). Seed data with `npx tsx scripts/selftest.ts` (writes `.data/`). Signed-in views: build with the `AUTH_*` vars, start with `E2E_FAKE_AUTH=1 OWNER_EMAIL=...`, and send `x-test-user: <email>` from Playwright (`extraHTTPHeaders`). The theme is stored JSON-encoded: `localStorage.setItem('ih-theme', JSON.stringify('dark'))`. Freeze time with Playwright's `context.clock.setFixedTime` for repeatable screenshots.

For live checks against real APIs from a cloud sandbox, Node's built-in fetch ignores `HTTPS_PROXY` unless run with `NODE_USE_ENV_PROXY=1`. Don't hammer Yahoo while testing: it rate-limits the IP for minutes.

`scripts/i18ntest.ts` enforces that every key in `src/lib/i18n/en.ts` exists in all 8 language files under `src/lib/i18n/` (en, vi, zh, ja, ko, es, fr, de). Any new UI string needs all 8.

`.env.example` lists every environment variable the code reads, with its default; `v14test` fails if code reads one that isn't listed.

## Architecture

**Pipeline (`src/lib/pipeline.ts`)** is the core; who follows what lives in `interests.ts`, stored briefings in `briefings.ts`. `buildDigest` fetches news (`news.ts`, feeds in `config.ts` `SECTION_FEEDS`), market data (quotes, macro, sectors, technicals, cached 10 min), and the calendar, then calls `analyze()` and returns a `Digest`. Briefings make no calls (v18): predictions are their own job (below). What gets priced is decided by `coverage(section, interests)`:
- My Interests: `BENCHMARKS` + the user's tickers, US sectors, mood from SPY.
- World/US/Vietnam: never personal stocks. `config.ts` holds `SECTION_STRIPS` (labeled strip groups, copied onto `Digest.strip`), `SECTION_GROUPS` (`WORLD_GROUPS`/`US_GROUPS`/`VN_GROUPS`: the markets the AI makes calls on, passed to the prompt as "interests"), `SECTION_MACRO`, and `MOOD_BENCH` (SPY / ACWI / ^VNINDEX.VN; the mood breadth set is world indexes or VN large caps instead of US sectors).

Callers:
- `refreshShared(section, lang)` for world/us/vn: one digest per language, stored at `digest:<section>:<lang>`. Prediction calls are recorded and graded per section (`SHARED_CALLS`: `calls:world|us|vn`); `/api/track?section=` serves them.
- `refreshInterestSet(interests, lang, uids)`: one digest per distinct interest set, keyed `ib:<hash>` where hash = sha1(normalized interests + language). Users with identical interests share one briefing.
- The scheduler (`scheduler.ts`, see Scheduling below) runs both: a shared section is one unit (English, then the Vietnamese translation), an interest set is one unit; prediction runs are units on their own lane.

**LLM (`src/lib/llm/`)**: each job has a "route" in `models.ts` with its own model order (Claude first if `ANTHROPIC_API_KEY`). Predictions get gpt-oss-120b: `predShared` 120b → Gemini Flash-Lite 3.5 → 3.1 → gpt-oss-20b; `predAdmin` 120b → 20b → Flash-Lite; `predUser` 120b (only beyond the reserve) → 20b → Flash-Lite. Briefings start on Flash-Lite: `shared`, `adminAuto`, `adminManual` Flash-Lite 3.5 → 3.1 → 120b → 20b; `userAuto` Flash-Lite → 20b → 120b (beyond the reserve); `userManual` Flash-Lite → 20b. `translate` qwen → Flash-Lite (never the briefing models); `ask` 20b → 120b. Groq limits are per model (200K tokens/day each), Flash-Lite 500 requests/day each. `models.ts` records real token use per model per day (`llm:usage:<model>`), cools a model down after a 429 (longer when the daily quota is gone), and keeps enough 120b tokens for the shared and admin predictions still due today (`reserveFor120`; `scheduledPerDay` is counted from `timetable.ts`, ~16 shared + 4 admin runs a weekday). If every model fails, a briefing gets the rule-based analysis (`rules.ts`); a prediction gets nothing (`generateJSON` throws, the scheduler retries once). Free providers get a "compact" prompt; `fitPrompt`/`generateJSON` trim headlines to stay under Groq's ~8k tokens/minute. Briefing output is validated against `schema.ts` (no calls since v18), predictions against `predict.ts`. `prompt.ts` holds the analyst rules, per-section focus, and Vietnam-specific rules/clock (`VN_RULES`, `vnMarketPhase`). The historical playbook the model must prefer over memory is `analogs.ts`.

**Predictions (`predictions.ts`, v18)**: a separate AI job from briefings. Each run calls ONE market: Vietnam (`VN_GROUPS`), US (`US_GROUPS`), or one World market (`WORLD_MARKETS` in `markets.ts`: Japan, China & HK, Europe, US stocks, oil, gold), or one interest set's part (`interestPart`: interests whose first ticker is `.VN` run on the Hanoi clock, the rest on New York's). Two runs per market per weekday (`timetable.ts`, in the market's local time): before market (daily + weekly calls) and mid-day (daily only). Every prediction works from the latest data: before the AI is called, each market's benchmark must have the latest finished session's close (after `freshenQuotes`) and, once its session has opened, a live price (a US-hours index or future with no live level of its own may use its same-hours ETF's move today, since mid-day calls are measured in %); otherwise the run is **unavailable** (no AI call, `unavailable` stored on the set with what was missing, shown on the card, retried once by the scheduler), and calls on any other ticker without the latest data are dropped. The prompt (`llm/predict.ts`) says how each call is graded and, per ticker, where today's call is measured from (previous close, or the live price "NOW"). After the model answers: calls on other tickers are dropped, a call on a ticker other than a market's benchmark is kept only if one of the run's headlines names it (`headlineMentions`), `alignAction` and `calibrate` apply, each call gets `phase`, `madeAt`, `gradeDate`, `gradesAt` (the close). Stored at `pred:<scope>` (latest daily run and latest weekly run; scopes `vn`, `us`, `world:<m>`, `ib:<hash>:us|vn`), recorded into the section's or set's call store, translated on read (`translatePredictions`, all of a section's markets in one call, `tr:pred:<scope>:<lang>`; Vietnam pre-translated into Vietnamese). After an interest set's run, `predictionAlerts` (call changes, high confidence) go to its users. Each run's input (snapshot, macro, technicals, calendar, track record and headlines; not the rules) is kept at `pred:<scope>:input:<phase>` for 8 days and served at `/api/predictions?section=&inputs=1`, so a prediction can be audited line by line. `/api/predictions?section=` serves them; Ask AI, the stock page, catch-up, the watchlist and the morning email read them (`callsOf`).

**Keeping the last AI briefing**: a rule-based result never replaces an AI briefing (`storeBriefing` in `briefings.ts`). It's saved at `<prefix>:rules` and the failed run at `<prefix>:aifail`; `/api/digest` returns `aiFailedAt`, the page shows a banner and readers can switch to the rule-based copy (`?variant=rules`, cached 15 min, rebuilt on demand within `RULES_DAILY_LIMIT`; the choice is saved per device).

**Track record (`track.ts`)**: prediction calls are recorded (`recordCalls`) and graded against prices. Ids: `<session>:<ticker>:d` (before market), `:m` (mid-day), `:w` (weekly); calls from before v18 have no `phase` and count as before market. The session is `dailyTarget` on the ticker's own exchange (today's if it hasn't closed, else the next trading day: weekends and the exchange's holidays in `holidays.ts` are skipped; an early close ends the session early, `closeUtc`/`sessionClosed`). A call made after its session opened is measured from the price then (`baseChg`, its move since the previous close, so it works with any price series; the flat band narrows by sqrt 1/2); without a live price it's `noLiveBase`: graded, not counted. Weekly calls grade at `endDate` = the 5th trading day counting the start (`nthWeekday(date, 5, tz)`, holidays skipped); if that day has no bar but a later one exists (or 48 h passed), the previous session is used (`gradedOn`). A daily call on a day in the holiday table is `closed` at once (no waiting); on a closure the table doesn't know (Seoul, Shanghai, Mumbai have no table; or a date it lacks), a daily call whose day has no bar (a later bar exists, or 48 h passed) is `closed`: market closed, not graded. Call stores: `calls:<interest hash>` per interest set, `calls:world|us|vn` for shared sections. Grading uses `getQuotes(..., { allowStale: false })`: never the stale fallback; a close the daily source hasn't posted yet comes from `freshenQuotes` (intraday), so calls grade within the hour as `provisional` (the source) and are re-graded from the official close on a later pass, which then decides. A session counts as over 15 min after its own exchange's close (`SESSIONS` in `markets.ts`; an ETF stand-in follows New York); the scheduler tick grades every store at most hourly (`gradeAll`), and prediction runs grade too. Up/down calls are right on the sign, and a move inside the band is `noResult`; flat calls must stay inside `flatBand` (a third of the ticker's typical daily move over 20 sessions, 0.15-1.5%, x sqrt 5 for weekly), stored as `band`. `computeStats`: the headline is the up/down hit rate with a 90% Wilson range and the 'always up' baseline, both by independent ticker-day (`rateByDay`: calls on one ticker, horizon and graded session share one outcome), and the skill over it; flat calls, Brier, per horizon, per phase, per action (`actionReturn`), per ticker, uncounted and closed counts, and pending calls with `gradesAfter`/`closesAt`. After the model answers, `calibrate` pulls each call's shown confidence toward its level's real hit rate once that level has 20+ graded calls (weight n/(n+20)) and attaches `record`; the model's own number stays in `aiConfidence` and is what `recordCalls` stores. `trackRecordText` feeds all of this into the prediction prompt (briefing prompts no longer get it).

**Prices** (all unofficial, keyless; verified from a cloud server Nov 2026):
- `yahoo.ts`: every Yahoo call goes through `yahooJson` (max 3 in flight, 90 s cooldown after a 429, no retry on the second host). Prefer `yahooSpark` (20 symbols per request, closes only) over per-symbol charts.
- `vnmarket.ts`: Vietnamese symbols are `CODE.VN` for any listing and `^VNINDEX.VN`/`^VN30.VN`/`^HNX.VN`/`^HNX30.VN`/`^UPCOM.VN` for indexes (`VN_INDEXES` maps each source's code). Order: DNSE (daily + 1/5-min/1H, stocks in thousand VND) → Vietcap (one symbol per POST, full VND) → VNDirect (daily, many codes per request, thousand VND; zero-volume pre-open rows skipped). All normalized to full VND. Yahoo has no usable VN index series.
- `market.ts` `getQuotes`: one spark batch for non-VN symbols, one VNDirect batch for VN ones, bounded per-symbol fallbacks, then the `px:last` last-good blob (quotes flagged `stale`). `chart.ts` `getChart`: VN → DNSE/Vietcap/VNDirect/Yahoo; others → Yahoo/Nasdaq; saved daily history (`chart:<sym>`) as a stale fallback. `getLiveQuotes` batches the same way and is cached 25 s per instance. `technicals.ts` uses spark 1y (close-only bars) and VNDirect.
- `worldmarket.ts`: real world levels when Yahoo refuses the server. VNDirect's public data API (same host as VN prices, Bloomberg-sourced) has daily closes for world indexes (`stock_prices`: S&P 500, Dow, Nasdaq, Nikkei, Hang Seng, Shanghai, DAX, FTSE, CAC, KOSPI, Nifty...), `commodities` (WTI, Brent, COMEX gold...) and `currencies` (USD/VND, EUR/USD, USD/JPY, USD/CNY...); the US Treasury's daily yield-curve CSV gives `^TNX`. Daily only, posted the next day (~03:00-07:00 UTC), so every value carries its date (`dailyOnly`). For US-hours markets with a same-hours ETF (`SAME_HOURS_ETF`: ^GSPC/SPY, ^DJI/DIA, CL=F/USO, GC=F/GLD) a newer ETF session carries the official close forward (`estimatedVia`, shown with ≈); in the same session the ETF only supplies the 1-day chart's shape (`shapeVia`). Never estimate non-US indexes from US-hours ETFs.
- Yahoo-only symbols with no real source (Euro Stoxx 50, DXY, VIX, Bitcoin) fall back to tracking ETFs priced by Nasdaq (`PROXIES` in `symbols.ts`); the quote/chart keeps the original symbol and sets `proxy`, and the prompt gets "level unknown, % moves only". Live overlay rule (`canOverlay` in `live.tsx`): same basis, or a real level replacing an ETF stand-in; never an ETF price over a real level.
- Live quotes (`getLiveQuotes`) for VN symbols come from the same 1-day chart the chart sheet shows (DNSE's daily series has no bar for today during the session), so the strip and the chart can't disagree. Each live quote has `session` (exchange-local date) and `intraday`; the strip sparkline is that session's path against the previous close, colored like the % chip (daily history is gray).
- `eastmoney.ts` (v18): Eastmoney's public intraday series (`push2his.eastmoney.com` trends2, keyless) for Nikkei, Hang Seng, DAX, FTSE, Euro Stoxx 50, S&P 500, Dow and WTI: the latest session's minute prices (Beijing time) and the previous close. It's a `getChart` 1-day source (so live quotes, the strip and the chart sheet agree) and feeds `freshenQuotes`. Its "NDX" is the Nasdaq Composite (not used); Shanghai and KOSPI timed out from the cloud; requests one at a time, one retry on a network error or 5xx (never on a 429), cached a minute (failures 15 s), last good answer saved in the store (`em:<sym>`: gives the previous close when a request fails; older than 10 min it isn't live, the chart is flagged stale).
- `freshenQuotes` (`market.ts`, used by `marketData` for briefings and predictions, and by grading for provisional grades): daily sources post closes hours late (Nasdaq's history in the evening, VNDirect's world closes the next morning), so a quote whose latest bar is older than the latest finished session gets that close from Eastmoney (indexes, WTI; its previous close must match ours within 0.3%) or the same provider's 1-day bars inside regular hours (US stocks/ETFs and ETF stand-ins; Nasdaq's 1-day series includes after hours, and its intraday "previous close" field is unreliable, so it isn't used), marked `closeVia`; no fill may move more than 25%. Eastmoney futures sessions are dated like CME's (18:00 New York starts the next day). Still without an intraday source from the cloud: Shanghai, KOSPI, Nifty, gold, FX pairs (dated daily closes).
- TCBS (Cloudflare check), Stooq (JS bot check), CNBC (Akamai) refuse servers; don't reintroduce them. Don't use API keys scraped from websites.

**Languages (`translate.ts`)**: every briefing is generated in English (`currentInterestSet` always returns `lang: "en"`, so the interest hash ignores language and readers of any language share a set); `display` is the person's single chosen language (stored as `settings.briefingLanguage`, kept in sync with the UI language by the page). Readers get translations. `translateLatest` sends only the text fields (`textSlots`), caches `tr:<prefix>:<lang>` per briefing version (`generatedAt`), and dedupes concurrent requests; `/api/translate` is called by the page when a briefing's `language` differs from the UI language. Translation (v19): chunks run two at a time, paced by reserved tokens per minute (`GROQ_TPM` x 0.94; the scheduler's third chunk waits for the minute, a reader's goes to Flash-Lite at once, `onFull`), no chunk starts after 50 s (route) or 120 s (scheduler pre-translation); when a run fails its finished chunks are kept (`trc:<hash>`, 24 h) so a retry only redoes the rest; a partial failure backs off 2 min (nothing finished: 10 min, `tr:<prefix>:<lang>:failed`); a store lock (`tr:<prefix>:<lang>:lock`, lifetime from chunks x providers x timeout, `translateWorstCaseMs`) makes two instances share one translation (the loser waits for the winner's cached copy or a failure recorded after it started waiting); `releaseLock` deletes only your own lock (Lua script on Upstash) My Interests briefings are pre-translated after each refresh (scheduler, catch-up, first briefing: `pretranslateSet`) into the languages of the set's followers seen in the last day (`followerLanguages`), never English, within `PRETRANSLATE_DAILY_TOKENS` a day (default 50K; the scheduler gives the admin's set first, then the sets with most followers; the rest translates on read). Don't regenerate a briefing just to change its language.

**News times**: some `.vn` feeds stamp Hanoi time as UTC; `fixFeedTimes` in `news.ts` shifts a `.vn` feed back 7 h when its items are in the future and clamps future times elsewhere.

**Headlines (`headlines.ts`, v18)**: refreshed with no AI. World, US and Vietnam every 15 minutes by the scheduler tick (`news:<section>`). An interest set (`news:ib:<hash>`) only while someone who follows it has the page open: each `/api/news?section=interests` request (the page polls the visible tab every 5 min; a tab nobody is on doesn't mark its set) marks the set as being read (`noteReading` → `news:active`), and the tick refreshes sets read in the last 35 min (`ACTIVE_MIN`) every 30 min; a reader who signs in or comes back to a list over 30 min old gets it fetched right away in the background (`refreshing: true`, the page asks again after 12 s). Nobody reading, no fetches. A briefing build also writes its list. A host that answers 429/503 rests 30 min (`news:cool`, in `fetchFeeds`). A briefing keeps the headlines it cited (its `sourceIds` index its own `news`); the page shows the live list, with "Key" matched by headline id and titles translated where the briefing's translated copy has the same headline (`newsFor` in `section-data.ts`).

**Time zones (`zones.ts`, v18)**: one setting per person (`settings.timeZone`, "auto" = the device's), also kept per device (`ih-tz`), synced like the language. `usePrefs()` gives `tz`, `timeAt` ("08:15 Hanoi") and `marketTime` (the market's clock, plus "01:15 your time" when the reader's differs). Every absolute time follows it with its zone named; charts and the open/closed pill stay in exchange time; calendar event times are labeled in their source's zone (ET).

**Search (`search.ts`, `vnlist.ts`)**: merges the VNDirect listing of every VN stock/ETF (cached a day in `vnlist`, built-in fallback list, accent-insensitive via `fold`), index/commodity names from `symbols.ts` `SYMBOL_LABELS`, and Yahoo search; ranked, Vietnamese results boosted for `lang=vi`. Following a stock from search creates a one-ticker interest (`src/lib/follow.ts` builds its news query; VN tickers get Vietnamese Google News in `news.ts`). `src/components/search.tsx` holds the sheet and `useFollow`; the page refreshes the personal briefing once when the sheet closes, not per tap.

**Storage (`store.ts`)**: `getJSON/setJSON` over Upstash Redis (`KV_REST_API_*`) or local JSON files. No database schema; the key layout is the contract.

### Auth and multi-user

Two modes, chosen by env (`src/lib/mode.ts`):
- **Single-user** (default): `APP_PASSWORD` (sent as the `x-app-password` header) for the owner, optional `VIEWER_PASSWORD` for read-only guests.
- **Multi-user**: when `AUTH_SECRET`, `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` are all set. Auth.js v5 (`src/auth.ts`, Google, JWT sessions, no DB adapter). Signed-out visitors can read; writes return 401 `{error:"signin"}`, which the client turns into a sign-in sheet (`prefs.tsx` `api()`).

Per-user isolation uses AsyncLocalStorage (`src/lib/context.ts`). Route handlers wrap their work in `gate(req, {user?}, fn)` from `src/lib/users.ts`, which checks access and runs `fn` inside `withUser(uid)`. Any per-user key must go through `ukey(k)`, which returns `k` for the owner and `u:<uid>:k` for everyone else. The owner (`OWNER_EMAIL`, or the single-user owner) keeps the legacy unprefixed keys, so existing data survives the switch to multi-user mode.

Security (v19): alert emails go only to the signed-in Google account's own address (`emailBlocked` in `alerts.ts`; the owner may use any). `PUT /api/alerts` refuses another address, and an older stored address that doesn't match is kept but never sent to (the tab says so); test sends are capped per person (`ALERT_TEST_DAILY_LIMIT`, 3). Feed and source links are http(s) only (`safe-url.ts`, at parse time and in every href). `/api/refresh` is POST only. `next.config.mjs` sets nosniff, a strict-origin-when-cross-origin referrer policy, X-Frame-Options DENY, a minimal Permissions-Policy and a CSP of only frame-ancestors/base-uri/object-src (a script-src policy needs nonces and a browser pass first). Route errors to visitors are generic (the cause goes to the server log); `/api/track` validates `?section=`.

Tests and E2E fake the session with `setSessionResolver()` or, outside Vercel, `E2E_FAKE_AUTH=1` plus an `x-test-user: email` header.

### Scheduling and cost controls

The timetable is one table in `src/lib/timetable.ts`. Briefing slots are UTC and run every day (weekends at the weekday rate since v18): World 4, US 5 (02:15, 12:30, 15:30, 17:00, 21:20), Vietnam 5; the admin's interest set 6 times (`interests:admin` slots plus the `interests:all` ones), everyone else's 5 (01:15, 04:35, 08:10, 12:30, 21:20 UTC; 04:35 added in v19). Prediction slots have a `tz` and run in the market's local time on its trading days (weekdays minus the market's holidays: `startsOn` in `timetable.ts` drops the occurrence, so no run, no "unavailable" note, no late alarm, and the AI reserve counts one run fewer), so summer time never puts a before-market run after the open; before-market runs start 75-120 min before the open so several pokes and a retry land in time: Japan 07:30/11:45 Tokyo, China & HK 08:00/12:15 HK, Vietnam 07:45/11:35 Hanoi (with interest sets' Vietnam parts), Europe 06:30/12:00 London, US 07:30/12:00 New York (US, US stocks, oil, gold, interest sets' US parts). To change a time, edit that table only: nothing else repeats the times. Holidays and early closes are edited in `holidays.ts` only; from Dec 1 each year `scripts/v19/row09-holidays.ts` fails until next year's tables (with sources) are added.

Only users seen in the last day (`SCHEDULED_ACTIVE_DAYS` in `users.ts`, the owner always) get scheduled interest refreshes; someone back after longer gets a catch-up: `/api/me` refreshes their briefing in the background when it's over 12 h old (`CATCH_UP_AFTER_MS`, counts against `AUTOGEN_DAILY_LIMIT`) and returns `catchUp` so the page waits for it. Price alerts reach users seen in the last 30 days.

`src/lib/scheduler.ts` runs it. Anything can call `GET /api/cron/tick` (`Bearer $CRON_SECRET` or `$TICK_SECRET`) at any time; the route answers at once and works in `after()`. Each tick takes a Redis lock (`takeLock`, overlapping pokes do nothing), runs price alerts if due (every 20 min, 13:00-22:00 UTC weekdays, no AI), grades (hourly), refreshes headlines that are due, then runs ONE unit and calls the tick again via `appUrl()` if it ran one. Units are on two lanes, predictions (120b first) and briefings (Flash-Lite first); each lane keeps 65 s between its units (`sched:lastUnit:<lane>`), and the lane that can go first goes. Every unit records an attempt in `sched:<date>:<slot>`, so the chain always ends. Each item has its own deadline (`itemEnd`): a before-market prediction until the market's open, a mid-day one 90 min, a briefing until the same briefing's next slot (max 6 h); past it the item is marked "missed: too late". Rules: a briefing written since 30 min before the slot is skipped (manual refreshes count); an AI failure is retried once after 20 min (predictions have no rule-based fallback, so a second failure is a missed run); interest sets go admin first, then stalest (briefings) or a fixed order (predictions). The tick answers 503 for an hour after a slot goes late (not finished 60 min after its time), so the caller reports it. `/api/status?schedule=1` (public, no secrets) lists the last 24 h of slots and the last tick; the admin's Status panel shows it, plus "AI use today" per model against its free allowance (`aiUsage`, admin only).

AI ceiling (v19): `available()` in `models.ts` refuses a model that has used `AI_USER_CEILING` (70%) of its free day (Groq tokens, Flash-Lite requests) to visitor routes (`userAuto`, `userManual`, `ask`, `predUser`, and a signed-out visitor's translation, marked with `withCeiling()`); shared, admin (the owner uid is exempt), scheduled-translation and other runs go on to the usual 97%, so a visitor never drains a model the shared briefings need. `userAiBusy` only decides the reply: when every model in the chain is past the ceiling, the entry points (non-admin refresh and Ask AI, first briefings and catch-ups via `autogenAllowed`, `/api/me`, guest translation) answer `busy` (503; the page shows `ai.busy`) and count nothing. Per-address limits (`ipKey`: IPv4, or an IPv6 /64): signed-out translation starts `TRANSLATE_IP_DAILY_LIMIT` (10) a day, then the shared `TRANSLATE_DAILY_LIMIT` as the outer cap (one pipelined INCR+EXPIRE request per start, `incrWindow` in `store.ts`); `/api/quotes` and `/api/chart` share `PRICE_IP_PER_MIN` (90) a minute, counted in memory per instance (no Redis commands).

Pokers (only an interval; none repeats the times): Vercel Schedules in `vercel.json` (every 15 min, every day since v18: about 2,980 of Hobby's 5,000 runs a month; Hobby: 15-min jitter, 5,000 runs a billing period, going over blocks every schedule), cron-job.org every 30 min (set up by the owner; it emails on a 503), and `.github/workflows/refresh.yml` every 3 h, every day (GitHub's schedule is unreliable on this private repo). Shared sections are pre-translated into Vietnamese only; other languages are translated on first read. An interest set is pre-translated into its recently seen followers' languages (see Languages). Manual refresh: the admin can refresh any section (`REFRESH_DAILY_LIMIT`, default 10, best model); signed-in users can refresh only their own My Interests (`USER_REFRESH_DAILY_LIMIT` 5 a day, `USER_REFRESH_GAP_MIN` 90 min apart, `userManual` route); every press writes a new briefing and the reply carries the quota, which `/api/me` also returns for the button badge. A newly saved interest set gets its first briefing in the background (`ensureInterestBriefing`, via `after()` in `/api/interests`, capped by `AUTOGEN_DAILY_LIMIT`), and the page polls until it appears. Daily caps live in `ratelimit.ts`. Yahoo refuses both Vercel and GitHub's runners (429), so a GitHub-side price relay doesn't work; refresh.yml keeps a `yahoo_test` dispatch input to re-check. Keep new features inside these free-tier limits.

### Frontend

Single page: `src/app/page.tsx` loads data and composes components; its state is split into hooks in `src/components/shell/hooks.ts` (viewport and layout, saved tab, new-headline dots, refresh-button state, shortcuts), and everything loaded per section lives in `src/components/shell/section-data.ts`: the briefing, live headlines and predictions, the rule-based copy, translate-on-read and the post-follow briefing poll. `dueLoads` (pure, pinned by `scripts/v19/row03-section-data.ts`) decides what is due from the clock, the visible tab and how long the page was hidden; `useSectionData` is the adapter (checks every 30 s and on `visibilitychange`). First paint loads all four sections once (strip, catch-up and the new-headline dots need them, and tab switches stay instant); after that only the visible tab is kept fresh: headlines and predictions every 5 min, the briefing every 10, all three when the reader returns after 5+ min hidden, and nothing while the page is hidden. Switching to a tab whose data is older than that loads it at once. A hidden page loads nothing; a failed load is forgotten (`tracked`) and retried after 30 s, 60 s, 2 min, capped at 5 min; a translation reply is saved only if the reader still wants that language. Components are named by feature (see the code map). Client-side preferences (theme, language, password, read state, saved headlines) live in localStorage via `prefs.tsx`, always wrapped in try/catch. Styling is one global stylesheet (`src/app/globals.css`) with CSS variables for light/dark; the mobile layout uses a bottom tab bar (`.tabbar`) and hides `.desktop-only` elements.

- The price strip (`MarketStrip` in `sections.tsx`) takes labeled groups; for shared sections the page builds them from `Digest.strip` (or `SECTION_STRIPS` for older digests) overlaid with live quotes. Mouse users get arrow buttons and drag-to-scroll.
- Background: a fixed `.ambient` layer (drifting radial color fields, dot matrix, grain) whose palette follows `data-section`; colors are `@property`-registered so tab switches morph. Cards/strip use translucent `--material` with backdrop blur; `prefers-reduced-motion` and `prefers-reduced-transparency` are honored.
- Multi-user visitors: My Interests shows `InterestsGate` (sign-in) instead of content; visitors land on World (Vietnam if the UI language is vi). The setup checklist is only for single-user mode or the admin.
- Charts format times in the exchange's time zone (`exchangeTz` in `symbols.ts`); the 1-day header names the session date when it isn't today. The page header date, "Up next" and the calendar follow the tab's market (Vietnam: Hanoi; shared tabs get their market groups' calendar, never personal earnings). Number formatters (`fmtPct`/`fmtPrice`) tolerate missing values; keep it that way, data comes from many free sources. Index levels keep 2 decimals, currency pairs 4 (`priceDigits`).
- Wide screens (≥1280px, `isWide` in `page.tsx`): sections and actions in a left `.sidebar` instead of the top bar, Ask AI docked in `.chat-dock`. Every way of asking goes through `openAsk(q?)` (docked panel when wide, sheet otherwise). The sidebar folds to a 64px icon rail (`[`, saved as `ih-side`; its toggle is top-left in both states and icons never move, labels fade) and the dock folds to a 56px rail whose reopen button sits where the close button was (`]`, `ih-dock`); the shell keeps all three grid columns so both animate (`--spring`), the dock stays mounted (inert when folded), and there's no floating Ask button on wide screens; the sidebar's Headlines item and the header News button jump to `#headlines` (`N`). `components/ask.tsx` holds the chat: conversations saved per account by `/api/ask` (`chatId`) in `lib/chats.ts` (30 chats × 30 messages), listed/deleted via `/api/chats`; suggestions built from the briefing on screen (`suggestionsFor`), follow-up chips after each answer; no extra AI calls.
- The Predictions card (`components/predictions.tsx`) sits under the briefing: per market, the latest daily run ("Before market"/"Mid-day", made and graded times via `marketTime`) and the weekly run, each call a row that opens to its trigger, rationale and risks; World's six markets sit in a grid on wide screens; it says when the next run is (`nextPredictionRuns`), and that there are none on weekends.
- A prediction's action must agree with its direction: the prompt says so and `alignAction` (pipeline) replaces contradictions (up + Sell/Trim/Avoid → Hold, down + Buy/Add → Wait, down + Hold → Wait without positions), keeping the model's in `aiAction`.
- Movers' numbers are overwritten from the price snapshot after the model answers (`alignMovers`); tickers not in the snapshot are dropped. A mover's reason survives only if one of its `source_ids` headlines names the stock (`headlineMentions`), otherwise it reads "No clear news".
- Native controls follow the chosen theme, not only the system's: `<option>` gets explicit `--surface`/`--label` colors (Windows draws it white otherwise), scrollbars are thin and themed (panels show theirs on hover), autofill uses the surface color. The account menu opened from the sidebar is portaled to `body` (`.acct-menu.floating`), because the sidebar's blur would clip it.
- Every overlay (sheets, catch-up, password) calls `openOverlay()` from `primitives.tsx`: it locks the page with body `position: fixed` and tracks `visualViewport` into `--app-h`/`--app-top`, because iOS `vh` includes the area behind the browser bars. Sheets keep their header outside the scrolling `.sheet-body`.

## Conventions

- UI copy is plain and direct; the AI is told the same (no hype, specific risks, calibrated confidence).
- The AI only ever sees holding weights and gain %, never amounts (`positionsAsText`).
- Interests: the first ticker is the benchmark used for the outlook and the track record.

## Working with the owner

These are the habits from past sessions. Follow them without being asked.

**Starting a session**
- Read `docs/HANDOFF.md`, then restate the goal and the rules that apply in a few lines before doing anything.
- Before starting, ask every question needed to make the task clear, so the work hits what the owner actually wants: scope, priorities, expected behavior, edge cases, limits, models, schedule, UX, what "done" looks like. Put them in one numbered list. Give lettered options where they help and mark the one you recommend. The owner answers by number ("1 B, 2 yes").
- Then give a plan before running anything: the steps in order, the files and services each touches, how each will be tested, the AI and free-tier cost, the risks, and what will need the owner (accounts, tokens, a merge). Wait for the owner's go. After the go, build without more check-ins, and say so if the plan has to change along the way.
- "Use all of the token" means: keep working through the whole task list without stopping for approval. If the context gets long, write a summary that keeps every decision, file change and open item so nothing is lost.

**Stress testing** ("stress test", "test every detail", "to the last minute")
- Test each goal end to end against real data from the cloud sandbox (`NODE_USE_ENV_PROXY=1`), not only the offline mocks. Go easy on rate-limited sources.
- Prices, charts and timing must agree everywhere. Compare the strip, the chart sheet and the briefing for the same symbol: level, % change, chip and sparkline color, session date, exchange time zone, and stale/estimate/proxy labels.
- Audit at least one real AI briefing line by line. Every level, %, date and reason must trace back to the data the model was given. An invented fact is a bug: fix it with a prompt rule and a code guard (overwrite numbers from data, require source ids, drop what can't be backed).
- Check all 8 languages, phone and wide screens, light and dark. Phone overlays need a check with a short visual viewport (browser bars showing).
- For any change, count the AI calls and tokens per day against the free-tier limits in `models.ts` and the schedule.
- Report each finding with its evidence (the URL, the number, the screenshot), fix it, and add a regression test to that round's `scripts/v<N>test.ts`.

**Research and ideas**
- When a data source or outside service is involved, research before building: find the options, test the real endpoints from the sandbox, and prefer official, keyless, free sources. Write down what was rejected and why (see the Prices section).
- Suggest ideas the owner didn't ask for when they clearly help, ranked by value against effort and free-tier cost. Give one recommendation, not a survey, and separate "do now" from "later".
- Push back on the owner's ideas too: give the other side and the failure cases, and say plainly when something won't work or costs too much.
- Reports for the owner (competitors, research, audits) are published as an artifact with sources linked and unverified figures marked as such.

**Delivering**
- One short-named branch per round (`v12`, `v13`, ...).
- Before pushing: `npm test`, `npm run typecheck`, and `npm run build` both with and without the `AUTH_*` env vars.
- Update this file for architecture changes, and add a section to `docs/HANDOFF.md` for the round: what changed, what was verified and how, what wasn't, and open items.
- Ask before merging to `main` (it deploys) unless the owner said to merge without asking. After a merge, check production with read-only GET requests only. Don't wait for the build inside the session (no polling loops, no background waits): schedule a check-in (`send_later`) about 5 minutes after the push and end the turn. The check-in confirms the new build is live (something only it has: a new CSS rule, UI string or API field), then checks the endpoints, then does a real-browser pass (wide and phone, no console errors). If the build isn't live yet, it schedules itself again rather than waiting.
- Refactors that must not change the UI: screenshot the views before and after with the same seeded data and a frozen clock, and compare pixel by pixel (`compare -metric AE`); report the counts.
- When a result can only be checked later (a deploy, a market close, an hourly job, the next scheduler tick), schedule a check-in (`send_later`) instead of holding the session or polling.
- On long tasks, post a one-line status now and then.
- End with: what changed, what was verified, what wasn't, open risks, and the one question that decides the next step.

**Lines not to cross**
- Never send write requests to production without credentials, and never probe it with them.
- No scraped API keys, no browser user-agent tricks to get past a site that refuses servers, no bypassing rate limits.
- Keep the owner's personal details out of code, docs, commits and requests to outside services.
